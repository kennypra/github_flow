READING THE HUB

What a model name tells you

Llama-3.1-8B-Instruct-GGUF-Q4_K_M
  • 8B — parameters (billions) → rough memory / compute cost
  • Instruct — tuned to follow instructions/chat (vs. a raw base model)
  • GGUF — a file format for local runtimes (LM Studio)
  • Q4_K_M — quantization level (4-bit): smaller + faster, small quality trade-off

NOTEParameters ≈ how big · quant ≈ how compressed · instruct ≈ how it behaves.

CONCEPT

Quantization

Representing weights & activations at lower precision (FP32 → INT8 or 4-bit) to cut memory and compute.

  • Fits smaller hardware — consumer GPUs, laptops
  • Faster inference, lower latency and energy
  • Trade-off: some accuracy loss, usually small at 8-bit / 4-bit

NOTEThis is what lets an 8B model run on your laptop at all.

Vanderbilt MS-DS  /  BootcampCollaboration Frameworks

CONCEPT

Distillation

Train a smaller student model to mimic a larger teacher — learning from the teacher's outputs rather than from scratch.

  • Result: a smaller, faster model that keeps much of the teacher's capability
  • Why "distilled" variants exist on the Hub

NOTEDistillation shrinks the model itself; quantization shrinks the numbers. Different knobs.

CONCEPT

PEFT — parameter-efficient fine-tuning

Freeze the base model; train only a small set of new adapter parameters (e.g., LoRA).

  • Fine-tune on modest hardware
  • Ship tiny adapter files, not a whole new model
  • Swap tasks without duplicating the base

NOTEThe practical path for most student & research fine-tuning.

AGILE

What is Agile?

A way of working in short, repeated cycles called sprints — plan, build, review, adjust, repeat. Here's a sprint at the DSI:

  1. Backlog development — collect & refine the list of work worth doing
  2. Sprint planning (start of the week) — choose what the team commits to this sprint
  3. Coding meetings through the week — office hours, pair programming
  4. Sprint retrospective (end of the week) — review what got done, discuss, reset goals for next week

NOTEA sprint is about a week. At the retro you mark issues done — or, as often in data science, re-strategize based on what you learned.

PLANNING

Issues & boards

Issues
  • One issue = one thing to do
  • Bug, feature, or experiment
  • Answers "what needs doing?"
GitHub Projects
  • A board over your issues
  • Todo → In Progress → In Review → Done
  • Where your sprint lives

A good issue is written so anyone could pick it up. It should include:

  • Context & objectives — the background and what "done" achieves
  • Technical details — approach, files, constraints, links
  • Acceptance criteria — the checklist that defines done
  • Deadline — when it's due

SAFETY

Branches keep main safe

main is always the working version. Your branch is a sandbox — experiment freely; main is untouched until review passes.

Keep branches short-lived
The longer a branch lives, the more main moves underneath it as teammates merge their own work — making the eventual merge harder. Small branches, merged often.

NOTEThis is how you stop overwriting each other.
